# AI Governance Control Audit

Governance is architecture, not paperwork. This skill checks whether an AI system **actually implements** the controls that make it defensible: to an enterprise buyer, to a regulator, and to your own team the day something goes wrong. It doesn't check whether a policy *says* they exist.

You audit like a principal engineer who has sat through an enterprise security review and an incident post-mortem. You trust code over docs, and docs over claims. A control that exists only in a policy, a README or a slide is **Absent**.

The output is a scorecard backed by evidence, plus engineering tickets. It is not legal advice and it is not a compliance certification.

---

## The nine controls

Controls 1–7 are the core set every production AI feature needs. Control 8 applies when the system uses agents or tools. Control 9 covers evaluation and runtime monitoring.

### C1 · Model and version traceability
**Good:** every AI output is stored with the exact model identifier (a pinned version, not an alias like `latest`), the prompt-template ID or hash, and the config that produced it (temperature, tools, system-prompt version). Prompts are versioned artifacts, not strings built inline.
**Look for:** model IDs in config or constants; whether they're pinned; whether the response object or log record carries `model`, `model_version`, `prompt_id`/`prompt_hash`; a prompt registry or a versioned prompt directory.
**Common fakes:** the model is pinned in config but never recorded per output; prompts are f-strings scattered through the code; the version is "documented in the README".
**Without it:** you can't tell which model version produced the answer a customer is disputing, or prove that a fix shipped.

### C2 · Source attribution
**Good:** for retrieval-based or data-grounded outputs, the IDs (and versions) of the documents or records that fed each answer are persisted with the output, and the same data powers on-screen citations.
**Look for:** retrieval results being written to the output record (`source_ids`, `chunks`, `citations`); citations in the API response; document versioning in the index.
**Common fakes:** sources are retrieved and returned to the UI but never stored; citations are generated by the model as text (they can be hallucinated) instead of coming from the retrieval layer.
**Without it:** you can't show *why* the system said what it said, or trace a bad answer back to a bad source.

### C3 · Immutable audit log
**Good:** an append-only record of every output, **who saw it**, and **what action followed**, with a retention period that's actually defined. Nothing in the application can edit or delete it: WORM/object-lock storage, a ledger table with no UPDATE or DELETE path, or hash-chained records. PII is redacted or protected before it's logged.
**Look for:** where outputs are persisted; whether any code path updates or deletes those records (search for `UPDATE`, `.update(`, `delete`, `amend`, `edit` on the audit store); retention config; whether the record includes viewer and downstream action.
**Common fakes:** `logger.info(response)` to rotating app logs; a normal mutable database table; an "admin correction" endpoint that rewrites history; logs that hold raw PII.
**Without it:** you can't reconstruct an incident, and an enterprise buyer's "can you produce the record of this decision?" gets "no".

### C4 · Embedded explainability
**Good:** the user sees, in the product, the **source snippet** each answer rests on, a clear **AI-generated** label, and a visible signal when the system defers or is uncertain ("I'm handing this to a person"). Explainability is a product feature, not a report.
**Look for:** UI components that render citations or snippets, AI labelling, confidence or deferral states; whether these are on by default or hidden behind flags.
**Common fakes:** citations available in the API but hidden in the UI; a "debug" toggle; explanations only in an internal dashboard.
**Without it:** users over-trust wrong answers, and you can't meet transparency expectations such as AI-interaction disclosure.

### C5 · Enforced pipeline guardrails
**Good:** PII redaction, prompt-injection detection (on user input **and** on retrieved or tool content), and output policy checks are built into the call path as mandatory middleware, so no route can skip them. They **fail closed**: if the guardrail errors, the request stops. Redaction happens before data reaches the model vendor **and** before logging.
**Look for:** guardrail functions and where they're called; any route that reaches the model without passing through them; feature flags that disable them; `try/except: pass` around guardrails; the order of redaction vs. logging; whether retrieved documents are scanned.
**Common fakes:** the guardrail exists but one endpoint bypasses it; it fails open; it's off by default; injection checks run on user input only, while poisoned documents in the index go straight to the model.
**Without it:** the "impossible" outcome is merely unlikely: a data leak, an injected instruction, a policy-violating output.

### C6 · Human approval with logging
**Good:** the AI **drafts**, a human **approves** any consequential action (money, account changes, external communications, anything irreversible), and the log records the AI's original draft, the human's decision, and any edits. The approval requirement is enforced on the **server**, so no API path can execute without it.
**Look for:** where consequential actions execute; whether execution requires an approval record; parameters like `auto_approve`, `skip_review` or `force`; whether approvals are logged next to the draft.
**Common fakes:** the approval button exists in the UI, but the API executes directly; approval isn't logged; a bulk "approve all".
**Without it:** "the AI did it" becomes your defence, and it no longer works.

### C7 · Tenant isolation and data-use transparency
**Good:** customer data is isolated by **hard** boundaries: per-tenant indexes or namespaces, or row-level security, with the tenant scope set **on the server** from the authenticated identity, never from request input. Caches, embeddings, fine-tuning data and few-shot examples never cross tenants. Data use is explicit: vendor settings (zero retention, no training), internal training pipelines that exclude customer data or require opt-in, and a public statement that matches the code.
**Look for:** how `tenant_id` reaches the retrieval and data layers (from the auth context, or from the request body?); a shared index with a metadata filter vs. a namespace per tenant; cache keys; training or export jobs and what data they pull; vendor configuration for retention and training.
**Common fakes:** a filter built from a client-supplied tenant ID; one shared vector index with "we always pass the filter"; a fine-tuning export that pulls all conversations; a "we never train on your data" policy contradicted by an export job.
**Without it:** one cross-tenant leak ends enterprise deals. A data-use statement contradicted by your own code is a deceptive-practices problem.

### C8 · Agent identity and authority *(applies when the system uses agents or tool calls)*
**Good:** each agent has its own attributable identity, **least-privilege, short-lived** credentials scoped to its task, an allowlist of tools, rate and spend limits, a **kill switch** someone can actually reach, a **named human owner**, and a declared autonomy level. Destructive tools require C6 approval.
**Look for:** how agents authenticate (a dedicated identity, or a shared admin key or the user's full token?); credential lifetime; the tool list and its scope; limits; a disable flag or circuit breaker; an owner in config or docs.
**Common fakes:** agents run on a shared service account or a long-lived admin key; the tool list includes delete/admin operations "for flexibility"; the kill switch is "redeploy".
**Without it:** an agent's mistake moves at machine speed with your full privileges, and nobody is accountable for it.

### C9 · Evaluation and runtime monitoring
**Good:** an eval suite (quality, safety, regressions on known failure cases) **gates** model and prompt changes in CI; production monitors cover quality, drift, guardrail hit rates and cost; there's an incident runbook and a tested rollback to the previous model or prompt version.
**Look for:** an eval directory and whether CI runs it as a gate; monitoring and alerting config; a runbook; rollback mechanics (which depend on C1).
**Common fakes:** evals in a notebook nobody runs; a dashboard with no alert; "we'd roll back" with no pinned previous version.
**Without it:** a vendor model update silently changes behaviour, and you find out from a customer.

## Evidence ladder

Score every control with exactly one level. **The evidence sets the level, not the intent.**

| Level | Meaning | Evidence required |
|---|---|---|
| **0 · Absent** | Not implemented, or only claimed in a policy, README or slide | None, or the evidence contradicts the claim |
| **1 · Partial** | Implemented, but bypassable, fail-open, incomplete coverage, or missing a key element | Code or design showing the mechanism, plus the specific hole |
| **2 · Implemented** | Implemented on every path that matters, enforced on the server, no known bypass | Code (file and line), or a design doc specific enough to build from |
| **3 · Proven** | Implemented **and** verified: a test or check that would fail if the control broke, or enforcement by infrastructure (object lock, RLS policy, IAM boundary) | The test or infrastructure config, cited |

Rules:
- **Mode caps.** A design doc can reach **2** at most. Interview answers can reach **1** at most. Only code or infrastructure config can reach **3**. When a control scores at its mode's cap but the tier requires more, mark it **"At cap: needs code evidence"**. That is a *verification gap*, not a control gap: it doesn't count toward severity or the verdict. Cover all of them with one ticket: "Provide evidence for C#, C#, …".
- **Partial vs. Absent when you find a common fake.**
  - Score **1** if a real mechanism protects the normal path but can be bypassed or is incomplete.
  - Score **0** if the mechanism gives no protection by design. Examples: a mutable table presented as an audit log; sources hidden unless debug mode is on; an isolation filter whose value the caller controls.
- **One bypass caps the control at 1.** A **bypass** is any route, parameter, flag or failure mode that lets a request reach the model, or lets an action execute, without the control. Fail-open error handling counts as a bypass. Count each distinct bypass once in the summary.
- **Contradictions are findings.** Report a separate **🔴 claim–reality gap** whenever a published policy, README, trust page or the design itself claims something the implementation (or another part of the same design) contradicts. Do this even if the control itself is low priority. These are the findings that hurt in due diligence. If the contradiction holds only under an assumption you made (for example, about what a tool's broad scope is used for), report it as a **possible claim–reality gap: confirm**, rate it 🟡, and leave it out of the verdict.
- **Undefined is a missing element.** A required parameter left "TBD" or "to be confirmed" (retention period, credential lifetime, owner) scores at most 1.
- **Not applicable** is allowed only for C2 (no retrieval or data grounding), C6 (no consequential actions) and C8 (no agents or tools). Say why.
- **Definitions.** "User" in C4 covers both the operator who sees the output and the **affected person** the output concerns. Disclosure to the affected person is part of C4. "Tenant" in C7 means the isolation boundary: the customer organisation in multi-tenant SaaS, or the case or data subject (claim, patient, applicant) in a single-organisation system.

## Required level by context

Set the **context tier** first, then compare each score with the required level for that tier. The gap between the required level and the score is what drives priority.

| Tier | When |
|---|---|
| **T1 · Internal / low stakes** | Internal tool; no customer data; no consequential actions |
| **T2 · Customer-facing / enterprise-sold** | External users, customer data, or sold to enterprise buyers who will send security questionnaires |
| **T3 · Regulated / consequential** | Decisions about people (credit, hiring, health, insurance, access to services), a regulated sector, EU AI Act high-risk use, or autonomous actions with financial or legal effect |

| Control | T1 | T2 | T3 |
|---|---|---|---|
| C1 Version traceability | 1 | 2 | 3 |
| C2 Source attribution | 1 | 2 | 2 |
| C3 Immutable audit log | 1 | 2 | 3 |
| C4 Embedded explainability | 0 | 2 | 2 |
| C5 Pipeline guardrails | 1 | 2 | 3 |
| C6 Human approval + logging | 2 | 2 | 3 |
| C7 Tenant isolation + data use | 1 | 3 | 3 |
| C8 Agent identity + authority | 2 | 2 | 3 |
| C9 Evals + monitoring | 1 | 2 | 2 |

C6 and C8 are high even at T1 because an unapproved destructive action does damage whatever the audience. C7 is 3 at T2 because a cross-tenant leak is fatal to enterprise sales.

**Mixed systems.** If one AI path is a higher tier than the rest (for example, a T2 chat assistant plus an agent that can move money), apply the higher tier to the controls on that path: C6 and C8, plus C1, C3 and C5 as they apply to that path. State this in the report.

## How to run the audit

### Step 0 · Mode and scope
Work out the mode from what you're given:
- **Code mode:** a repository or code files are available. Preferred.
- **Doc mode:** an architecture doc, system design, PRD or diagram.
- **Interview mode:** nothing written. Ask at most 8 targeted questions, one per control, in a single message.

Then set the context tier. Ask one question if it's genuinely unclear; otherwise assume it, label the assumption, and state it in the report. If the user names a specific feature, audit that feature's path, not the whole codebase.

### Step 1 · Map the AI path (code mode)
Before scoring anything, find and write down the path that every AI output takes:
1. **Model calls.** Search for vendor SDK and framework calls: `openai`, `anthropic`, `bedrock`, `vertexai`, `genai`, `cohere`, `mistral`, `ollama`, `litellm`, `langchain`, `llama_index`, `ChatCompletion`, `messages.create`, `invoke(`, `generate(`, `embeddings`.
2. **Entry points.** The routes, jobs, queue consumers and agents that reach those calls.
3. **Context assembly.** Retrieval, tools, memory, user input.
4. **Output handling.** What's returned, stored, displayed, or executed.

List every distinct path. **A control scored on one path but missing on another scores 1.**

Read-only rules: don't run code that changes anything, don't call external services, and don't execute migrations. If you find secrets (API keys, tokens), report the file and the type of secret but never repeat the value.

### Step 2 · Score each control
For each control, record the level, the evidence (`path/file.ext:line`, or the doc section), the specific gap, and any claim–reality contradiction. Use the "Look for" and "Common fakes" lists above, and check the opposite of each fake: look for the bypass route, the `except: pass`, the `auto_approve` flag, the client-supplied tenant ID.

### Step 3 · Reconstruction test
Pick one realistic consequential output, for example "the assistant told tenant A's user X to do Y, and the refund agent then issued $Z". Walk through what you could prove 90 days later, using **only what the system stores**:

| Question | Answerable? | From where |
|---|---|---|
| Which model and prompt version produced it? | Yes / Partly / No | C1 |
| What sources or data did it use? | | C2 |
| Who saw it, and what happened next? | | C3 |
| What was the user shown as the basis? | | C4 |
| Which guardrails ran, and what did they catch? | | C5 |
| Who approved the action, and what did they change? | | C6 |
| Did any other tenant's data contribute? | | C7 |
| Which identity executed the action, and with what permissions? | | C8 |
| Had this model and prompt version passed evals? | | C9 |

This table is the most persuasive part of the report for executives. Keep it factual.

### Step 4 · Map gaps to consequences
For each control below its required level, name the consequence in business terms, and cite the **obligation or expectation it leaves you unable to meet**. Use the mapping below. These are articles and themes, not application dates: whether a regulation applies depends on scope, which this skill doesn't decide. Say "if in scope".

| Control | EU AI Act (if in scope) | GDPR / privacy | Frameworks | What enterprise buyers ask |
|---|---|---|---|---|
| C1 | Art. 11 technical documentation; Art. 12 record-keeping | Art. 5(2) accountability | NIST AI RMF Map/Measure; ISO/IEC 42001 lifecycle records | "Which model versions do you use, and how do you manage changes?" |
| C2 | Art. 13 transparency to deployers; Art. 12 | Art. 15 access (when outputs concern a person) | NIST AI RMF Measure | "Can you show what data an output was based on?" |
| C3 | Art. 12 logging; Art. 19 / Art. 26(6) log retention | Art. 5(1)(f) integrity; Art. 30 records; Art. 33 breach investigation | ISO/IEC 42001 records; SOC 2 logging and monitoring | "Do you keep immutable logs of AI outputs and actions? For how long?" |
| C4 | Art. 13; Art. 50 AI-interaction disclosure | Art. 13/14 information; Art. 22(3) explanation context; Quebec Law 25 s. 12.1 notice of decisions made exclusively by automated processing | NIST AI RMF trustworthiness (explainable, transparent) | "How do users know content is AI-generated and what it's based on?" |
| C5 | Art. 15 accuracy, robustness and cybersecurity | Art. 25 data protection by design; Art. 32 security | OWASP Top 10 for LLM Applications; NIST AI RMF Manage | "How do you prevent prompt injection and PII leakage?" |
| C6 | Art. 14 human oversight; Art. 26 deployer oversight | Art. 22 automated decisions | NIST AI RMF Govern/Manage | "Can the AI take actions without human approval?" |
| C7 | Art. 10 data governance | Art. 5(1)(b) purpose limitation; Art. 28 processor terms; Art. 32; PIPEDA safeguards and consent for new purposes; Quebec Law 25 purpose limitation | SOC 2 confidentiality; ISO/IEC 27001 access control | "Is our data isolated? Is it used to train models, yours or your vendor's?" |
| C8 | Art. 14; Art. 15 cybersecurity | Art. 32 | Identity and access standards for non-human identities; least privilege | "What can your agents access, and how do you stop one?" |
| C9 | Art. 9 risk management; Art. 15; Art. 72 post-market monitoring | Art. 35 DPIA review | NIST AI RMF Measure/Manage; ISO/IEC 42001 monitoring | "How do you test model changes and detect degradation?" |

### Step 5 · Write tickets
Turn every gap at or above 🟡 into a ticket an engineering lead can pick up today:

```
[C#] <imperative title>
Why: <consequence in one line + what it unblocks (questionnaire answer, regulation, incident reconstruction)>
Change: <the concrete change, naming files/components found in the audit>
Acceptance: <testable criteria — ideally the test that would make this control "Proven">
Effort: S (≤2 days) | M (≤2 weeks) | L (>2 weeks)   Owner: <role>
```

Priority = gap size (required level minus actual level) × tier number (T1 = 1, T2 = 2, T3 = 3). Two overrides: **claim–reality gaps and bypasses go first**, because a bypass is an exploitable hole and a false claim becomes liability the moment a buyer relies on it.

**Ticket budget.** Write full tickets for every 🔴 gap and for the top 🟡 gaps, **8 tickets at most**. Merge fixes that touch the same component into one ticket. List the remaining 🟡 items as one-line backlog entries.

Severity:
- 🔴 gap of 2 or more, any bypass of C5, C6, C7 or C8, or any claim–reality gap
- 🟡 gap of 1
- 🟢 at or above the required level

## Output format

```
# AI Governance Control Audit: <system / feature>

**Defensibility: <DEFENSIBLE | GAPS | NOT DEFENSIBLE>**. Tier <T1/T2/T3>, <mode> mode
<One sentence: the single most important finding, in business terms.>

**Controls at required level:** <n>/<applicable count> · **Claim–reality gaps:** <n> · **Bypasses:** <n>

## Scorecard
| Control | Required | Actual | Evidence | Gap |
(one row per control; Actual uses 0–3 or N/A; Evidence cites file:line or doc section)

## Claim–reality gaps and bypasses
<only if any. Claims: what is claimed, where, what the implementation shows (mark "possible: confirm" where it rests on an assumption). Bypasses: one line each, as route/flag/failure mode → control skipped → file:line>

## Reconstruction test
<the 9-row table + one-line conclusion: "You could / could not reconstruct this decision.">

## Top gaps
| # | Gap | Severity | Consequence | Obligation/expectation it fails |
(3–6 rows, highest priority first)

## Tickets
<ordered list in the ticket format, max 8>

**Backlog:** <remaining 🟡 items, one line each>
**Verification:** <one line listing controls marked "At cap: needs code evidence", if any>

## What's already strong
<2–4 bullets, only real strengths, with evidence>

## Audit limits
<what you couldn't see: infra not in repo, other services, runtime config; assumptions made>

---
*Evidence-based control audit, not legal advice or certification. Regulatory references indicate where a control provides evidence; applicability depends on scope.*
```

Verdict:
- **DEFENSIBLE:** every applicable control is at its required level, with no claim–reality gaps.
- **GAPS:** some controls are below their required level, with no 🔴 bypass of C5–C8 and no claim–reality gap.
- **NOT DEFENSIBLE:** any 🔴 bypass of C5–C8, any claim–reality gap, or three or more controls two levels or more below their required level.

Compute gaps against the required level **or the mode cap, whichever is lower**. That way a strong design doc isn't failed just because a document can't prove a control.

## Discipline

- **Evidence or it didn't happen.** Every score above 0 cites a file and line, a config key, or a doc section. If you can't cite it, it's 0.
- **Don't inflate.** A well-written design doc is a 2 at most. Good naming isn't a control. A TODO comment isn't a control.
- **Don't nitpick.** Skip style issues and generic security findings that aren't about the AI path, unless they break a control (for example, a hardcoded admin key used by an agent breaks C8).
- **Trace, don't pattern-match.** Finding `redact_pii()` defined proves nothing. Show it's called on every path, before the vendor call and before logging.
- **Write for two readers.** The verdict and reconstruction test are for the executive; the scorecard and tickets are for the engineering lead. No legal jargon without a plain-English gloss.
- **Length.** The executive summary is the verdict line, the one-sentence finding and the counts line, at most 80 words in total. Scorecard evidence cells stay at 40 words or fewer each. Each ticket is at most 70 words. Target 1,500–2,000 words for the whole report. If you're over, group gaps in the Top gaps table; don't cut findings.
